# StuHelper Moderation

moderation 管理审核策略、任务、举报、作者申请、复核、处置结果、审计和反馈收件箱。reviews 和 resources 管理各自的正文与可见状态，通过公开 `Content` 接口执行决定。平台业务规则见[内容运营与审核](https://github.com/StuHelper/stuhelper/blob/develop/docs/spec/content-management.md)。

## 接口、依赖与数据归属

`module.yaml` 声明必需依赖 platform，可选依赖 verification 和 identity。`moderation.tasks` 依赖 identity。宿主注入 `Access` 与 `Content`，提供认证授权及当前对象状态，模块通过这些接口核验能力、学校和修订。

HTTP 任务、策略、健康和反馈接口位于 `/api/v1/moderation/`，使用当前会话。申请人和受影响作者可读取各自的回执，其他用户按当前学校的管理权限读取。`AccessibleTasks` 供通知装配批量筛选 1 至 100 个任务，只返回当前请求人能读取的 ID。

资料正文、交付及访问权益归 resources。登录用户的资料侵权投诉由 resources 校验材料和目标，经可信 `SubmitResourceComplaint` 端口登记。回执省略目标正文。

## 审核与复核

发布检查按学校、全局、内置默认的顺序解析策略。评课、导师评论与回复默认直接发布，资料默认待审核。策略可设置先审后发或先发后审。命中敏感词会拦截发布。配置端规范化词条并去重，具有配置权限的管理员可以试运行。

`Check` 只返回检查结果。内容模块提交正文后通过 outbox 发出事件，由 backend 转交 `Track` 创建待处理任务。追评任务绑定独立的 `append_id`，`approve_append` 和 `reject_append` 只处理该条追评。

新增举报检查当前准入。本人仍可为待审举报补充证据，资格失效或资格服务故障时也可补证。结案后重新举报需要重新检查准入。每个账号每分钟最多 10 次举报或投诉新提交，同键同请求沿用原回执。超限返回 429 和 `Retry-After`。

管理队列默认按创建时间升序，支持最新优先。个人回执按最近进展倒序。列表使用时间和 ID 分页。学校范围内提供状态与类型计数、同对象待办数及最多 20 项批量处置。批量预览与执行使用同一授权和动作校验，每项分别返回结果。

决定要求当前学校授权和内容修订。学校审核员处理本人内容的发布、恢复、评优、追评通过或驳回他人举报时受到回避限制，平台级权限可豁免。主内容处置生效或举报、巡检被驳回后，系统联动结案同校同对象且对象修订不高于决定修订的待审举报。

作者可以对已执行的不利决定申请一次复核。待审期间可补充理由和证据，结案后不能再次申请。复核人须具备复核权限且与原审核人不同。受影响作者的回执只展示允许公开的决定字段，违规类别与错误原因使用封闭枚举。

## 投递、审计与保留

决定先持久化，由 worker 每轮最多领取 50 项，在事务外调用内容模块。同一决定 ID 可以重试。对象修订冲突、无权限和对象不存在直接进入失败状态。暂时不可用按 5 秒至 1 小时退避，24 小时后转人工处理。停机取消后会限时回写已执行结果。

决定和终态分别写入同事务 outbox。backend 读取事件、监听 `moderation_outbox`、补读积压，并将终态交由通知消费者处理。消费者持久化后确认事件。每批最多 100 条，可在分页前排除最多 1000 个暂缓主题。事件字段见[审核事件契约](contracts/events.md)。

可信宿主通过 `Repository.ReadAudit` 查询按当前授权过滤的脱敏记录，单次最多 101 条。以事务可见性快照排除回填和延迟提交，实际修改或删除会使旧快照失效。字段与分页约定见[审核审计查询](contracts/audit.md)。

`Service.CleanupRetention` 返回分类清理数量。默认每类 200 条，上限 500。到期幂等回执和限流窗口保留 24 小时，已确认事件保留 90 天，常规审核审计保留 12 个自然月。`/api/v1/moderation/health` 供平台管理员查看决定和事件积压及反馈容量。

## 反馈收件箱

`feedback` 包保存邮件、附件引用、处理状态、负责人、内部备注、关联任务及回复记录。backend 负责邮箱连接和材料存储。读取、处理、回复分别使用 `moderation.feedback.read`、`moderation.feedback.manage`、`moderation.feedback.reply`，授权范围为全站及 moderation 模块。

反馈按接收时间和 ID 倒序分页，可筛选负责人、状态和可疑标记。支持分派、取消指派及关联站内任务或对象。更新使用修订号和幂等键。垃圾状态邮件须先转入处理中才能回复。回复先持久化为 `sending`，完成后记录 `sent`、`failed` 或 `unknown`，同键重试沿用原记录。

每封原始邮件最多 12 MiB，正文最多 200000 字节，最多 10 个附件且每个最多 5 MiB。原始邮件预算为 2 GiB，活动记录上限 10 万，清理摘要上限 100 万。总容量达到上限时暂停接收，服务器邮件保留待处理。

发件人邮箱地址按小写规范化，每小时最多完整接收 20 封。超限邮件仅入库摘要并标记为垃圾和可疑。模块按消息标识、发件人和内容摘要去重，并保存邮箱游标。访问审计省略邮件正文、发件地址和附件内容。

已结案记录按 UTC 保留 12 个自然月，每轮最多清理 50 条。清理限时删除材料对象，随后在事务内核对状态与修订。重新打开时停止清理，清理后的摘要用于阻止旧邮件再次导入。反馈审计另按 12 个月和每批 100 条清理。

## 本地检查

```sh
make setup
bash scripts/check-with-postgres.sh
```

以 `contracts/moderation.openapi.json` 为 HTTP 契约来源，执行 `make generate` 更新 SDK。迁移身份与运行身份分离，模块访问自己的 `moderation` schema。

`module.yaml` 的 `scenario_tests` 使用 `文件#测试函数` 指向实际测试。CI 在隔离 PostgreSQL 上验证准入、处置幂等、追评和复核、投递与审计、数据到期清理及反馈流程。
